## 3.1 Development Approach and Lifecycle

<Figure id="fig-3-1-kanban" />

### 3.1.1 Agile Kanban Planning

The proponents used Agile Kanban because the project contained changing institutional requirements and work items of different sizes. Kanban supports visible work states and continuous flow without requiring a fixed sprint duration. Studies of software teams report that Kanban can support changing priorities, coordination, and continuous delivery when teams adapt it to their working context (Ahmad et al., 2018).

Project planning used two linked Notion databases. CLOIE Backlog contained module-level work such as user access and authentication, academic structure, evaluation instruments, deployment, outcomes management, response collection, analytics, report export, and infrastructure. CLOIE Tasks contained the work needed to complete those module items.

Each task could record its module, priority, assignee, work type, description, Definition of Done, and related backlog item. The task board used the states Backlog, To Do, In Progress, Testing, and Done. Status-transition dates retained evidence of when a task entered active work, testing, and completion. The backlog also summarized progress from its related tasks.

Notion supported module planning and workload visibility. GitHub held the technical specification, discussion, implementation history, and review evidence for code changes. This separation kept the planning board readable while allowing complex changes to retain detailed acceptance criteria and technical records.

The process had no fixed iteration length. A work item advanced when its dependencies and acceptance conditions were understood. Priority could change after a client consultation, an adviser review, a defect, a security concern, or a newly discovered domain rule.

### 3.1.2 Iterative Delivery Lifecycle

The team used the following lifecycle for substantial changes:

1. A requirement, defect, stakeholder request, or technical concern entered the backlog.

2. The proponents investigated the affected workflow, domain rules, and current implementation.

3. The full-stack developer or the proponent responsible for the analysis wrote or refined the GitHub issue specification and its acceptance criteria.

4. Large changes were divided into vertical slices. The issue structure identified blocking work, work that could proceed in parallel, and the order needed to preserve a working system.

5. Implementation took place on a short-lived branch. Independent slices could use separate Git worktrees so that development and testing did not interfere with another branch.

6. The developer ran the applicable unit, component, database, browser, accessibility, build, and manual checks before or during pull-request review.

7. GitHub Actions and AI-assisted review identified failures or code concerns. The developer assessed each finding, revised the branch where needed, and reran the affected checks.

8. After the pull request met its acceptance criteria and quality gates, the change merged into main. The proponents then updated affected requirements, ADRs, context files, tests, and project records.

The full-stack developer used AI-assisted coding tools for bounded implementation, investigation, and review tasks. AI output did not replace repository evidence or human judgment. Every proposed change remained subject to diff inspection, automated tests, browser checks where applicable, and human acceptance before merge.

Feedback could reopen completed work. For example, changes in institutional responsibility led to revisions in outcome ownership and administrative workflows. Later architectural review also removed Dean enrollment oversight and changed the rules for PLO and CILO question bindings. These changes were recorded through issues, tests, documentation, and ADRs rather than being hidden in the final code.

Release checkpoints included working local builds, passing pull-request checks, non-production deployments, formal beta activity, and production-oriented verification. These checkpoints did not by themselves prove final acceptance. Chapter 5 and the supporting appendices contain the corresponding results and completion evidence.

## 3.2 Requirements Engineering and Stakeholder Engagement

Requirements engineering continued throughout the project. ISO/IEC/IEEE 29148:2018 treats requirements definition and management as lifecycle activities. System CLOIE applied this principle by keeping stable identifiers, acceptance criteria, change records, and traceability links as the system changed.

### 3.2.1 Stakeholders and Requirements Elicitation

The client consultations established the institutional problem, required evaluation instruments, respondent groups, expected reports, and the boundary between system evidence and academic decision-making. Adviser consultations addressed capstone scope, documentation, development approach, evaluation, and presentation.

The operational stakeholder groups represented in the system are the Secretary, College Dean, General Education Coordinator, Program Heads, Faculty Members, Students, Alumni, and Industry Partners. Their inclusion as system roles does not imply that every member of each group joined every consultation or validation activity. Chapter 5 and Appendix G identify only the groups that participated in recorded validation.

The proponents used client and adviser consultations, institutional document review, evaluation-instrument analysis, workflow analysis, interface review, implementation findings, and test results to refine requirements. The institutional instruments included the Post-Term CILO Evaluation Tool, Graduating Student Exit Survey, Alumni Evaluation Tool, and Industry Partner Internship Evaluation Tool.

Use cases described how each actor interacted with the system. Interface sketches and issue-level design work helped clarify workflows that written requirements did not fully resolve. These artifacts supported analysis, but they did not count as proof that a feature was implemented or accepted.

### 3.2.2 Requirements Analysis, Prioritization and Validation

The proponents assessed each request against the project objectives and boundaries. Work received higher priority when it supported evaluation context, controlled response collection, learning-outcome evidence, analytics, reports, security, data integrity, or a dependency needed by those capabilities.

The analysis also identified the actor and academic scope for each operation. A general statement such as "manage outcomes" was insufficient because ILO, PLO, and CILO responsibilities belong to different roles and contexts. The same rule applied to courses, assignments, evaluations, responses, analytics, and reports.

Priority reflected stakeholder need, dependency, architectural risk, security, data integrity, and readiness of the underlying model. Notion recorded operational priority, while the approved requirements and Appendix F provide the formal requirement priority and status.

Requirements were validated through consultation, issue review, implementation, automated tests, manual verification, and stakeholder validation. A requirement remained incomplete when its implementation lacked the acceptance or test evidence needed to support it.

### 3.2.3 Change Management and Traceability

A change began when new evidence contradicted an earlier assumption or introduced a new need. The proponents assessed its effect on scope, domain ownership, authorization, data, interfaces, tests, and deployment. Large changes received a GitHub specification and, when the decision affected several modules or would be difficult to reverse, an ADR.

The repository records changes such as multi-role accounts with an active-role context, General Education Coordinator ownership of ILOs, removal of Dean enrollment oversight, revised publication gates, institution-time-zone rendering, and expanded CILO question binding. These records show how the project corrected earlier decisions without rewriting its history.

Open proposals remain separate from implemented behavior. Email-password authentication and email notifications for published evaluations, including GitHub issues 621 and 629, remain pending until the team approves, implements, tests, and documents them.

Appendix F is the controlling Requirements Traceability Matrix. It connects each objective and approved requirement to acceptance criteria, design components, implementation evidence, tests, validation, status, and change references. The matrix retains stable OBJ, FR, NFR, SEC, DR, INT, UC, and TC identifiers. Code alone does not justify a Verified or Passed status.

## 3.3 Development Workflow, Collaboration and Configuration Management

### 3.3.1 Source Control and Trunk-Based Integration

System CLOIE uses Git and GitHub for source control. The repository contains the application, database schema and migrations, tests, specifications, ADRs, feature context files, deployment documentation, scripts, and engineering records.

The project used a lightweight trunk-based workflow. Main was the sole long-lived integration branch. The developer created short-lived feature, fix, refactor, documentation, continuous-integration, or operations branches and opened pull requests back to main. This avoided the additional staging and development branches used by Git Flow, which would have added coordination work without clear value for a project with one full-stack developer.

A pull request grouped the implementation, tests, discussion, CI results, and review findings for a change. Recent repository history shows repeated branch-to-main pull requests rather than a final bulk upload. Conventional Commit categories identify the purpose of commits, including feature, fix, refactor, test, documentation, build, CI, and operations work.

The chapter does not claim a required human approval count or a particular branch-protection rule. GitHub configuration and pull-request records provide the evidence for any such controls included in the final supporting material.

### 3.3.2 Issue Specifications, Vertical Slices and Parallel Work

GitHub issues served as executable specifications for substantial work. An issue documented the problem, current state, constraints, acceptance criteria, affected areas, and known risks. A large feature could use a parent issue with sub-issues that each delivered an independently testable vertical slice.

The slice plan identified blockers and parallel work. A slice normally included the affected user interface, service logic, authorization, persistence, and tests needed to produce a working result. This reduced the risk of completing one technical layer while leaving the user workflow unusable.

Separate Git worktrees allowed independent branches or AI-assisted coding tasks to proceed in parallel. Each worktree used its own branch and verification cycle. The developer reviewed and integrated the completed slices through pull requests rather than combining unreviewed outputs.

Notion tracked the module and task state. GitHub retained the technical discussion and code history. ADRs recorded cross-cutting decisions, while CONTEXT-MAP.md and feature-level CONTEXT.md files recorded domain terms, invariants, ownership, and module boundaries.

### 3.3.3 Code Review and Quality Gates

The developer ran focused checks while implementing a change. Pull requests to main then entered the GitHub Actions pipeline. The current pipeline separates static checks, node and DOM unit-test jobs, a risk-selected production build, database integration, and browser end-to-end testing.

Static checks run Prettier verification and ESLint on the affected files. Vitest runs the node and DOM test projects. Changes that affect application or production behavior trigger a Next.js production build. Database-sensitive changes use a disposable PostgreSQL service, replay the canonical migrations, load deterministic fixtures, and run the gated database-invariant suites. Browser-sensitive changes run Playwright against a production build with isolated CI authentication and desktop, mobile, and selected visual checks.

Separate workflows run code-intelligence checks and CodeQL security analysis. Scheduled verification adds deeper database, browser, cross-browser, production-authentication-boundary, and demo-isolation checks.

Pull requests may also receive AI-assisted review from Greptile or GitHub review tooling. The developer treats those comments as findings to assess, not automatic decisions. A change merges only after the relevant failures are corrected or the reviewer finding is resolved with evidence. The affected checks run again after revision.

### 3.3.4 Environment, Deployment and Configuration Management

The development and deployment model separates local development, continuous integration, non-production testing, and primary production. Local development uses Node.js, pnpm, and a local Supabase Docker stack. Development-only authentication remains disabled in production behavior.

The Coolify staging environment contains Dev and Preview application resources. The Dev resource supports a development server with hot reload through dev.system-cloie.app. The Preview resource runs a built non-main branch through preview.system-cloie.app so the team can inspect production-mode behavior before merging. The formal beta activity used the deployed non-production setup to make role-specific workflows available to representative users.

Primary production runs the main branch at system-cloie.app. Coolify builds the System CLOIE container, and Cloudflare Tunnel publishes the application and API domains. The deployment model supports redeployment after integration, but this chapter does not claim that the GitHub push webhook is currently verified from end to end.

System CLOIE uses independently operated, self-hosted Supabase backends. Local, CI, staging, beta or demo, and production data targets remain separate. CI uses disposable PostgreSQL containers and must not write test data to an institutional backend.

The repository documents public build variables and server-only configuration separately. Secrets, OAuth credentials, signing keys, and database credentials remain outside version control. Database migrations run as controlled deployment actions instead of running automatically when the application starts.

### 3.3.5 Documentation, Dependencies and Contribution Evidence

The project records difficult-to-reverse decisions in ADRs. CONTEXT-MAP.md indexes the feature-level CONTEXT.md files that define domain responsibilities, terms, and invariants. Specifications, runbooks, test documentation, and deployment inventories record details that do not belong in source-code comments.

The repository uses pnpm with a committed lockfile and a pinned Node.js runtime. The main stack includes Next.js and TypeScript, PostgreSQL through self-hosted Supabase, Prisma, Zod, React Hook Form, Tailwind CSS, Recharts, Vitest, Testing Library, and Playwright. Appendix E retains the detailed dependency versions, licenses, external-processing concerns, and operational requirements.

One proponent served as the full-stack developer. The other proponent supported systems analysis, documentation, testing coordination, consultations, and project presentation where the records show that work. Named contribution evidence comes from commits, pull requests, issues, authored documents, testing artifacts, and consultation records. The supporting appendices retain those details rather than relying on the initial division of labor.

## 3.4 Secure and Responsible Development

Security and privacy affected requirements, design, implementation, testing, and deployment. This follows the NIST Secure Software Development Framework, which treats security as part of the development lifecycle rather than a final inspection (Souppaya et al., 2022).

### 3.4.1 Identity, Authorization and Confidential Data

Primary production uses Supabase Auth with Google OAuth and approved institutional domains. The application separates the authentication identity from the System CLOIE domain user. An account may hold several assigned roles, but one server-validated active role controls the current session and authorization context.

Authentication does not grant unrestricted access. Server-side services check the role and the applicable program, course, General Education, assignment, deployment, or respondent scope. The codebase also contains negative tests for cross-role access and database policies.

System CLOIE retains identity where eligibility, response integrity, or duplicate prevention requires it. Authorized analytics and review views limit respondent identification according to the workflow. The manuscript therefore describes responses as confidential, de-identified, pseudonymized, or aggregated according to the actual view. It does not make an unsupported claim of absolute anonymity.

Free-text responses require stricter handling because a respondent may include identifying details. Raw comments remain subject to authorization and data-minimization rules. The AI boundary receives deterministic, de-identified evidence rather than unrestricted respondent text.

### 3.4.2 Validation, Secrets, Dependencies and Infrastructure

Forms use Zod schemas, while services enforce business and authorization rules that the browser cannot prove. PostgreSQL constraints, indexes, and database-invariant tests protect rules that must remain valid across interfaces.

A syntactically valid identifier does not establish ownership or access. Services therefore validate both the input shape and its domain meaning. Publication, respondent eligibility, academic scope, and response-finalization checks run on the server.

The application reads secrets and connection details from environment configuration. The repository contains an example environment file but does not commit operational credentials. The application container runs as a non-root user, exposes a health endpoint, and keeps schema migration separate from application startup.

Dependency locks improve reproducibility but do not prove that dependencies are secure. CodeQL, dependency review, update testing, and the Appendix E inventory support ongoing maintenance.

### 3.4.3 Backup, Recovery and Incident Readiness

Committed migrations and controlled seed data can rebuild local and disposable test environments. Production recovery requires more. It depends on retained database, storage, and configuration backups, an assigned operator, a restore procedure, and evidence from a restore test.

The current deployment inventory records database, storage, and configuration archives. Those copies share the production server. Automated backup retention, an encrypted off-server copy, and a recorded restore drill remain open operational work. Chapter 5 must report the verified readiness state without treating the existing archives as complete disaster recovery.

The turnover records must identify the future operator, maintenance process, credential custody, incident contact, rollback procedure, and recovery responsibilities. Actual credentials must not appear in the manuscript or appendices.

### 3.4.4 Responsible AI-Assisted Interpretation

System CLOIE separates deterministic analytics from optional AI-assisted interpretation. The application calculates counts, distributions, averages, completion rates, and other quantitative evidence. The AI provider does not replace those calculations.

When enabled, the server sends bounded, aggregate-derived qualitative evidence through an OpenAI-compatible interface. The input excludes respondent identifiers and raw comment text. The provider interprets the supplied structure and returns text for an authorized academic user to review.

AI output cannot authorize access, alter domain records, classify official outcomes, or make curriculum decisions. Academic personnel remain responsible for interpretation and action. Chapter 5 must identify the provider, model, configuration, limitations, and validation evidence used for the evaluated build.

## 3.5 Verification, Validation and Testing Strategy

Chapter 3 defines how the team verified and validated System CLOIE. Test counts, defects, participant results, acceptance decisions, and retest outcomes belong in Chapter 5 and Appendix G.

### 3.5.1 Automated Verification Layers

Vitest and Testing Library cover application logic, services, validation, components, and route behavior. Database-invariant suites verify migrations, constraints, row-level security, academic-state rules, publication, response lifecycle, user assignments, and related persistence behavior against a disposable database.

Playwright exercises complete role-based journeys against a production build. The CI configuration includes desktop and mobile Chromium projects, accessibility scenarios, cross-role privacy tests, failure-state checks, and selected visual baselines. Scheduled runs add Firefox and WebKit coverage where required.

The production build acts as a separate quality gate because type, bundling, server-rendering, or route errors may not appear in isolated tests. Risk selection skips expensive jobs only when changed files cannot affect the corresponding area. Static checks and unit tests continue to run on pull requests.

### 3.5.2 Test Environments and Data Isolation

Unit tests use fixtures, mocks, and isolated application data. Database and browser CI jobs start a disposable PostgreSQL container, replay migrations, seed the required fixture, run the tests, and discard the environment.

Playwright uses deterministic test accounts and a CI-only authentication path. Local development uses a separate development-only path. Primary production uses Google OAuth and cannot enable the development or CI path.

The Dev and Preview resources allow deployed inspection without using production data. Preview provides a built branch for production-mode behavior. Formal beta testing used non-production infrastructure with role-appropriate accounts. Appendix G records the validated build and environment.

### 3.5.3 Manual and Beta Validation

The proponents performed manual checks for visual quality, responsive behavior, error messages, interaction state, and workflow combinations that automated tests did not cover. The full-stack developer also inspected affected desktop and mobile paths while implementing and reviewing a change.

Formal beta testing allowed representative users to access the deployed system through the roles relevant to their work. The activity assessed whether users could complete the intended tasks and identify defects, usability problems, unclear content, or missing workflow rules.

Chapter 3 records the method only. Appendix G-2 must contain the validation type, build, date, mode, stakeholder groups, participant count, tasks, method, and findings. Chapter 5 reports the results after the records are reconciled. No participant count, pass rate, or acceptance decision is inferred from access to the beta environment alone.

### 3.5.4 Acceptance, Defect Handling and Retesting

A test begins from an identified revision or build with a reproducible environment. Database-dependent checks start only after migration and fixture verification. Browser checks start only after the application and test contract pass their health checks.

Acceptance criteria come from the approved requirement, GitHub issue, or Definition of Done. A successful test process is not enough when the observed behavior does not meet those criteria. Critical FR, NFR, SEC, DR, and INT items must link to observable criteria in Chapter 4 and Appendix F.

A failed test, review comment, manual finding, or stakeholder concern becomes an issue or validation record. The developer identifies the cause, revises the implementation or requirement, reruns the affected test, and performs related regression checks. Playwright retries remain disabled so that a failed run followed by a pass is not hidden as a clean result.

Appendix G-3 links each significant finding to its priority, revision, changed area, retest result, and closure status. Unresolved findings remain visible.

### 3.5.5 Evidence Retention

Evidence may include GitHub Actions runs, test reports, Playwright traces, screenshots, pull requests, commits, build records, database-test output, manual test records, and signed validation forms.

Appendix G-1 records system tests. Appendix G-2 records user or stakeholder validation. Appendix G-3 records findings, revisions, and retesting. Appendix G-4 records the final user or client validation summary and acceptance. A blank form or an unrecorded demonstration does not prove that validation occurred.

## 3.7 Feasibility and Sustainability

### 3.7.1 Technical and Operational Feasibility

The current implementation demonstrates technical feasibility. System CLOIE has a working feature-driven modular monolith built with Next.js and TypeScript, PostgreSQL and self-hosted Supabase, Prisma data access, Google OAuth, role-scoped workflows, migrations, automated tests, Docker images, and GitHub Actions.

The modular feature structure keeps domain rules near their components, services, schemas, and tests. ADRs and context files record cross-cutting decisions. The same application path runs against separate local, CI, non-production, and production backends.

Operational feasibility depends on institutional data, assigned role owners, participant access, training, and a maintainer after turnover. System CLOIE supports evaluation evidence and does not replace the institution's learning management system, student information system, grading process, curriculum authority, or accreditation decisions. Formal beta validation provides evidence about actual use, but Chapter 5 must report its results.

### 3.7.2 Schedule and Organizational Feasibility

Agile Kanban allowed the team to deliver vertical slices while requirements changed. The same flexibility created a schedule risk because late changes could displace documentation, validation, or operational work.

One full-stack developer handled the codebase. Issue slicing, automated tests, CI, ADRs, context files, and runbooks reduced dependence on memory, but they did not remove the continuity risk. The proponents must prioritize critical requirements and defer work that cannot be implemented and verified before final submission.

Institutional feasibility also depends on confirmed ownership of user administration, learning outcomes, deployments, data protection, hosting, backups, and incident response. The final turnover and acceptance records must name the responsible institutional unit or maintainer.

### 3.7.3 Economic Considerations and Sustainability

No verified cost-benefit calculation drove the selected architecture. The chapter therefore does not invent labor values, commercial-license savings, or return-on-investment figures.

The operating model may incur costs for the host, domain, network services, storage, backups, external APIs, maintenance, and future upgrades. Chapter 5 may report verified costs when the final deployment arrangement provides them.

Long-term sustainability depends on current documentation, recoverable data, dependency maintenance, tested migrations, monitored infrastructure, and institutional ownership. The Docker deployment, committed migrations, lockfile, automated tests, CI workflows, ADRs, context documentation, and runbooks support maintenance. Sustainability remains conditional until the team completes backup automation, an off-server copy, restore testing, credential transfer, and operator handover.
